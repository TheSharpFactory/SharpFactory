## Versioning rules

- Four parts: `A.B.C.D`. Each part goes 0–9.
- Every bump adds 1 to the last part. When a part would hit 10, it resets to 0 and the part to its left goes up by 1.
  - `1.0.0.9` → `1.0.1.0`, `1.0.9.9` → `1.1.0.0`, `1.9.9.9` → `2.0.0.0`
- One bump per completed change set (each piece of work that changes code).
- Every change set gets an entry in [RELEASE_NOTES.md](RELEASE_NOTES.md) (date, version, changes, commit details).
- Every published release gets a section in [CHANGELOG.md](CHANGELOG.md), written for users; it becomes the text of the GitHub release for the tag `v<VERSION>`.
- `VERSION` is the only place to edit: `Directory.Build.props` stamps it into every assembly (file and product version), the app's About page and toolbar read it from the assembly, and the release workflow checks that the tag matches it.

## Guiding principles

- **Free forever** (user, 2026-11-05). The Sharp Factory is free and open source; no paid tiers, licensing, subscriptions or accounts.
- The user owns the code and the thesharpfactory.com domain; the website stays as the download and documentation site.
- **Generated code targets .NET 10 and later only** (user, 2026-11-05); .NET 11 support to follow.
- **The SQL the generated code runs does not change** (user, 2026-11-05): it works; the SQL engine templates and query-building code stay as they are.
- **Generator output does not change** (user, 2026-11-05): generated code stays byte-identical to the reference solution; fixes that would alter generated files are dropped. Exceptions, decided case by case by the user: fixing output that does not compile today (SF-084, 2026-11-05); `<EnforceCodeStyleInBuild>false</EnforceCodeStyleInBuild>` in the project files Sync creates, so generated code never fails a build on a style rule (SF-090, 2026-11-05). The `.cs` files stay byte-identical.
- **Generated code is not tested inside the code repo** (user, 2026-11-05): it is generated, compiled and Sync-tested only in a folder outside the repo. Inside the repo it picks up the repo's strict `.editorconfig` and fails in ways real solutions never do (for example CA1822, SF-036). The repo is going to GitHub, so it holds no code generated by test runs (user, 2026-11-05); the old `DataAccess/` sample moved out in 1.0.9.9 (SF-048).
- **The app runs against test databases** (user, 2026-11-05), not production; reading a model may execute stored procedures; acceptable there for now, to be assessed later (SF-023).
- **The progress console is deliberately paced** (user, 2026-11-05): the progress must stay readable. The WPF app did it with `Thread.Sleep` pauses before closing its consoles; the Avalonia app (1.1.0.2) keeps the Add/Update progress log on screen until the user clicks Done, and the Sync log and report until the next run. Speed-ups below the UI aren't a goal.
- **C# rules** (user, 2026-11-05) for all of The Sharp Factory's own source (not generated code): full-bodied methods and `{ get; set; }` properties; no lambdas (LINQ included), local functions or switch expressions (switch statements are fine); `var` everywhere; PascalCase classes, methods and properties, camelCase parameters and variables, `_myField` private fields; every class `sealed`, `abstract` or `static`; classes used only in their own project are `internal`, and internal classes have only `public` or `private` methods (SF-085).
- **.NET 10, same code** (user, 2026-11-05): everything targets .NET 10, but the code stays as it is. No project pins the C# version (user, 2026-11-08, SF-137): each uses its target framework's default. Until 1.1.3.3 every project pinned `<LangVersion>11.0</LangVersion>`. The code stays classical C# (user, 2026-11-08: "use classical C# style programming... No switch expressions, no inline functions, no record type, no lambdas, no weird hacky shit like default values in interfaces, etc"): no switch expressions, no local functions, no records, no lambdas, no default interface members, and nothing of that kind.
